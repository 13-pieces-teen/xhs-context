# xhs-context 架构与接入合理性核验

核验日期：2026-11-19。本文记录计划书的证据和决策依据；产品范围以[主计划书](../小红书收藏上下文项目计划书.md)为准。

## 1. 结论与证据等级

**本地资料库 + CLI + Skill 适合当前单人、单机、Codex 优先的使用方式。项目成立的首要条件，是在约定的数据获取边界内，可靠地完成真实收藏夹的整夹接入。这个条件目前尚未验证。**

| 判断 | 当前依据 | 可以得出的结论 | 不能得出的结论 |
| --- | --- | --- | --- |
| 查询不需要 MCP 或独立服务 | 同机进程可直接访问文件和 SQLite；Skill 可指导调用脚本 | 可以用普通函数、CLI 和 Skill 形成完整调用路径 | CLI 天然更省 token、比 MCP 更快 |
| “看看收藏”可作为接入参考 | 固定提交的 README、扩展和解析器源码 | 页面导入、匿名解析、媒体归档的边界值得借鉴 | 上游已支持整夹同步，或批量成功率已经得到保证 |
| 中文全文检索需要额外处理 | SQLite 官方文档与本次合成实验 | 不能把默认 FTS5 当作完整中文检索方案 | 某个中文分词器或检索方案已经通过真实问题验证 |
| Python 核心能减少运行时组合 | SQLite 标准库接口、Python OCR 候选工具 | 值得优先验证 Python CLI、核心、同步进程和 OCR 的统一实现 | 本机已有生产可用的安装包、OCR 或依赖组合 |
| DeepSeek Harness 可后续接入 | 官方仓库及三个插件的固定提交 | 有本地检索、证据窗口和显式触发的参考 | 本项目现在需要开发 Harness 插件，或插件已兼容我们的数据 |

证据类型：

- **源码核验**：阅读指定版本，未安装运行上游产品。
- **机制实验**：使用合成文本在内存数据库中运行，只证明特定机制。
- **方案判断**：基于当前需求做出的工程选择，允许被后续实测修正。
- **NOT_RUN**：真实收藏夹、OCR、项目 CLI、Codex 工作流和地图写入尚未执行。

## 2. “看看收藏”：可借鉴的边界与需要新建的能力

核验版本：`feitangyuan/kankan-shoucang@a788e60177a90387f2c580bcec91d475cdf6044f`。

### 2.1 已核对事实

1. [README][kankan-readme]明确把批量同步和按账号、收藏夹采集排除在当前产品范围之外。它证明了单篇导入的实现路径，不能直接证明本项目的批量入口。
2. [匿名解析器][kankan-resolver]从公开页面中的初始状态寻找笔记，使用不带账号凭证的请求，限制目标主机、重定向、超时和响应体大小。它没有在失败后切换到登录态采集的流程。
3. 解析器对“成功”的要求较宽：有标题、正文或图片即可构成候选，最终也不会要求正文一定非空。因此业务层必须区分元数据、正文和媒体的获取状态。
4. 解析器和[页面数据脚本][kankan-page]均存在图片列表最多取 20 张的处理。本项目不能原样继承后把结果称为完整归档；超过处理上限或无法确认数量时必须报告缺口。
5. 页面脚本处理的是当前详情页的数据。不能由此推断收藏夹卡片已携带每篇笔记的完整正文和原图。
6. [扩展清单][kankan-manifest]使用 Manifest V3、后台 service worker 和本地回环地址，未申请 cookies、tabs、webRequest 权限。我们若使用 `chrome.storage.local` 保存待确认批次，需要新增 storage 权限。
7. 上游声明 AGPL-3.0-or-later。直接复用代码时记录具体文件、提交与许可；选 Python 实现并不自动消除派生代码的许可问题。

### 2.2 对本项目的影响

保留“用户打开页面 → 扩展取得页面可见资料 → 必要时匿名解析选中笔记的公开页 → 本地保存”的路径。新建整夹枚举、完整性判定、持久批次、重试、媒体缺口报告和检索数据模型。

入口必须先检查：用户的目标收藏夹是否能在网页上完整展示、是否有可靠的文件夹身份、是否能确认列表终点。只看到收藏总列表时，不能凭标题推断出原来的文件夹归属。

保存页面中实际出现的笔记 URL 与必要参数；用于匿名获取的实际链接和用于展示的规范链接分开记录。不自行生成访问签名，也不从只有 note ID 的记录推断一定可访问。

匿名解析仍然是程序化网络访问。更准确的表述是“页面导入与匿名公开页解析，不接管账号接口”，而不是“完全没有自动化或抓取”。本次没有验证平台对批量匿名访问的实际响应。

## 3. 扩展同步与本机传输

[Chrome service worker 文档][chrome-lifecycle]说明后台进程会因空闲等条件被终止，内存中的变量不能作为可靠任务记录。批次编号、未确认条目和任务进度必须持久化；恢复时允许重扫、去重，不承诺恢复到相同滚动位置。

[Storage 文档][chrome-storage]要求声明 storage 权限，`storage.local` 有配额且卸载扩展会清除数据。待发送队列只存有界元数据，达到上限时暂停继续枚举；大图和正文不堆进扩展存储。访问级别需限制，配对秘密只进入扩展受信任上下文。

本机通道的比较：

| 方式 | 优点 | 代价 | 当前决策 |
| --- | --- | --- | --- |
| 同步期间启动 loopback HTTP 接收器 | 与上游路径接近，便于观察请求和批次确认 | 用户需启动同步进程；需校验配对凭证、Origin、负载和目标地址 | 首个试点采用 |
| Native Messaging | 浏览器可按需启动本机宿主，不需要监听端口 | 增加宿主清单、扩展绑定、Windows 注册及安装维护 | 用户确有启动体验问题时再考虑 |

[Native Messaging 官方文档][chrome-native]支持上述进程模型，但不意味着它应在第一版与 HTTP 同时实现。

查询 CLI 不依赖任何接收器。同步入口只处理固定的导入请求，不提供任意 URL 代理、SQL、命令执行或任意路径写入。只有数据库提交成功后才 ACK；重复提交必须幂等。

## 4. 中文检索机制实验

复现：在项目目录运行 `python research/fts5_probe.py`。脚本只使用 Python 标准库和内存数据库，无网络访问、无真实收藏、无包或模型安装。

- [实验脚本](fts5_probe.py)
- [本次原始结果](fts5-probe.json)
- 实际运行环境：Python 3.12.7，SQLite 3.45.3。它们是本次实验环境，不是已选定的生产支持版本。

原文：`马德里小吃推荐，图二介绍土豆饼。`

人工分词对照：`马德里 小吃 推荐 图二 介绍 土豆饼`

| 查询 | 原文 + unicode61 | 人工分词 + unicode61 | 原文 + trigram |
| --- | --- | --- | --- |
| 马德里 | 0 | 1 | 1 |
| 小吃 | 0 | 1 | 0 |
| 土豆饼 | 0 | 1 | 1 |

数字是这个单文档实验中的命中条数。[FTS5 文档][sqlite-fts5]解释了默认 tokenization 和 trigram 的短词限制。实验说明需要中文预处理与短词通道；没有评估生产分词器、相关性排序或性能。

建议在候选实现中比较：

- 中文分词后写入 FTS，英文和技术标识单独规范化；[jieba][jieba]作为初始候选，使用自定义词典且记录词典版本。
- 小语料范围内的字面子串补充查询，用于短词、店名和技术标识；记录其耗时。
- 明确的别名表，以及 Agent 提供的少量查询变体。
- 只有真实问题在上述方法下持续漏召回，才试验本地向量召回。

索引文本和查询文本必须采用对应的分词策略。词典加载时间计入 CLI 启动成本；即使检索 SQL 很快，也不能忽略每次启动 Python、导入包和分词器的耗时。

## 5. 本地实现与 OCR 的选择

首选候选为：浏览器扩展使用 JavaScript/TypeScript，本机 CLI、接收器、队列、数据处理统一使用 Python。SQLite 通过[标准库 sqlite3][python-sqlite]访问；打包时仍需验证目标 Python 发行版包含 FTS5。

这是一项工程取舍：当前没有需要共用 TypeScript 的独立 Web 应用，Python 可以与 OCR 使用同一运行时。代价是需要移植上游 JavaScript 解析逻辑并维护对照样本。若真实试验表明直接复用上游代码节省了明显工作量，可以重新比较，但不为可能出现的 Harness 版本提前维持 Node 与 Python 双运行时。

OCR 初始候选为 [RapidOCR + ONNX Runtime CPU][rapidocr]。当前安装文档使用 `rapidocr` 与单独的推理引擎，且说明默认小模型可随包分发。具体版本与模型必须在实现时锁定、校验并预先准备；不能笼统假定一定要首次联网下载，也不能让一次日常查询触发下载。

本次没有安装、运行或比较 OCR。必须用真实图片测：长图、小字、截图表格、中英混排、西班牙语店名及重音字符。读取失败、识别为空、低置信度和模型不支持目标语言应分别报告。仅保留 OCR 文本不足以提供可靠证据，原图和区域位置必须可回读。

SQLite 的 [WAL][sqlite-wal]可支持短事务下的读写并行，但仍只有一个写者。本地队列足够当前范围，无需引入 Redis 或独立任务平台。备份使用[一致性快照接口][sqlite-backup]并复制快照引用的媒体，不能只在运行中随手复制主数据库文件。

| 项目 | 状态 | 所需证据 |
| --- | --- | --- |
| 用户目标收藏夹是否在网页完整可见 | NOT_RUN | 一份真实完整列表及人工复核记录 |
| 匿名详情与媒体的批量成功率 | NOT_RUN | 整夹运行日志，包含失败条目和完整分母 |
| 中断重启、重传、更新和移除 | NOT_RUN | 故障恢复与重复同步结果 |
| OCR 能否保留关键店名和技术词 | NOT_RUN | 原图与人工标注对照 |
| CLI 是否优于 Agent 直接读文件 | NOT_RUN | 相同资料、模型、任务的成对评测 |
| 地图地点是否识别正确并实际保存 | NOT_RUN | 外部地图查证与保存后的状态 |
| Python 包、CLI、扩展安装体验 | NOT_RUN | 干净环境安装和同机离线查询 |
| Harness 兼容性 | NOT_RUN | Codex 验收后，另行测试目标 Harness 版本 |
